# Architecture

## Stack and responsibilities

React renders the studio. Vite compiles TypeScript and provides development reload. Express runs on Node and optionally persists patches as JSON files. The browser's Web Audio API synthesizes, schedules, routes, analyses, and records sound locally.

```text
React controls / workspace
          │
          ▼
    Project (plain data) ───► autosave → localStorage
          │                      └── manual save → Node API → .data/
          ├────────────────► JSON export / validated import
          ▼
     AudioEngine
          ├── module factories → Web Audio graph
          ├── look-ahead scheduler → oscillator pitch/gate + drum hits
          ├── analyser → live scope and meters
          └── MediaStream destination → MediaRecorder → IndexedDB / download
```

## App versioning

`scripts/app-version.ts` reads the release series from `package.json` and derives a SemVer build identity from Git: `0.1.0+20.gabcdef0`, with `.dirty` for tracked/staged edits or untracked files. The commit count advances on every commit; the hash distinguishes branches with equal counts. Detached HEAD and linked worktrees are supported. Ignored dependencies/build output do not mark a checkout dirty. The npm `prebuild` step restores shallow history from origin before Vite starts, without changing HEAD; the CI entry point uses the same helper before validation. The version reader still rejects any history that remains shallow because its count is incomplete; source archives without Git receive an explicit `+source` identity. No timestamp, network request, generated source file, or Git hook is required.

The Vite plugin supplies one snapshot to the typed `virtual:app-version` module and emitted `version.json`. `AppVersion` displays a compact `v0.1.0+20` badge in the bottom-right footer, including on phones, with `*` for local edits and the full identity in its title/accessibility label. Development watches source changes and Git's HEAD/index/branch refs (including atomic replacement) to refresh the module after commits or checkouts. Production metadata is fixed at build time, so cached/offline sessions identify the code actually running rather than the latest code on a server. The existing offline build includes the manifest and versioned bundle in the content digest, creating a distinct atomic release even for an otherwise empty commit. This identity is independent of `Project.version`, which now uses v3 for patchable MIDI and expanded modulation footers.

## Module field guides

Each library item has an accessible question-mark button alongside Add. `domain/module-guides.ts` stores a required guide for every module type: overview, setup steps, numeric control descriptions, special controls, a tip, and a worked example with actual module/port endpoints. `compatiblePorts()` derives possible partners directly from registry socket directions and signal types, excluding the same module type. These are capability matches; the normal workspace rules still reject occupied inputs and feedback loops.

`ModuleHelpDialog` groups equivalent sockets (such as Mixer IN A/IN B), displays compatible modules, and lets the user explore their guides in the same native dialog with a local Back stack. Reading or navigating help does not edit the patch, add modules, change playback, or enter undo history. The separate explicit **Load demo patch** action opens a new editable demonstration through App’s normal project switch, which stops audio/capture and preserves the current owned patch. The loaded demo remains temporary until explicit Save patch; switching away from another unsaved demo discards it. The guide and module drawer close, focus moves to the workspace, and audio still waits for a user performance gesture. The shared Modal uses an accessible title, native focus trapping and Escape/backdrop dismissal. Related-guide navigation resets scroll/focus within the modal, and closing returns focus to the original library button. The mobile library stays open behind the guide so it is available on dismissal.

The guide layout lives in `components/module-help.css`. Instructions and connections are text/semantic HTML rather than an audio preview. Tests validate guide control coverage, signal-specific compatibility, and every worked example against the real patch validator. `module-demos.ts` derives loadable demonstrations from these same `example.connections`, applying optional `example.parameters` and per-instance overrides; each returns a validated project plus a declared transport/keyboard/pad/MIDI-test interaction and instructions. Guide endpoints may supply a teaching `instance` name to distinguish multiple copies of one type; the factory resolves those names to fresh module IDs, with conflicting type names rejected. These names/rows stay in guide metadata, outside saved patches. Optional registry-sized rows place each instance exactly once for comparison patches; other guides retain their DAG-column layout. Optional recipe interaction/instructions take precedence over inferred gestures, allowing a transport-first demo to include live pads. External kit lanes are selected from their actual wires; `demo-samples.ts` supplies an original local clap shared with the existing examples. Every copy owns fresh IDs and editable objects. `tests/module-demos.test.ts` treats these user-facing factories as the development fixture set, checking the complete catalog rather than a second list of testing recipes. Browser/audio QA should load these actual guide demos and perform their declared gesture. The Sample & Hold demo has three independent sources: eighth-note filter changes, small quarter-note pitch drift with longer Glide, and pad-triggered sampler-speed variation using the bundled clap. A manual Switch compares the three paths and a fourth dry reference. Only the third random source has TRIGGER IN connected; the other two keep following transport.

## Patch format and validation

`Project.version` is currently `3`. `parseProject` explicitly migrates v1/v2 input to v3 without mutating it. The coordinate migration preserves stored positions; additive control migrations and legacy pad-enclosure clearance also apply as described below. V2 permits finite signed world coordinates (within a ±1 billion numerical safety range) rather than positions constrained to an 1800×1200 rack. Old saves, samples, IDs, and routing remain intact; new saves/exports use v3, which older releases reject. The browser library keeps its existing storage keys so previous work remains discoverable. A patch contains its UUID, title, update time, tempo, root/scale, time signature, master volume, positioned modules, and directed cables. A module stores its registry type, UUID, position, parameters, optional eight scale degrees, an optional `drumPattern` map, and optional Drum kit or Mic sampler `samples`. Pattern and sample fields remain optional; the v1→v2 migration preserves their original contents. Drum machines must contain exactly the four named lanes of sixteen booleans; other module types cannot store a drum pattern. `-1` is a rest. Degrees `0…13` span two octaves of a seven-note scale; pentatonic degrees use its five-note table.

No AudioContext, AudioNode, React state, object URL, or recording blob is serialized into a patch. `parseProject` checks UUIDs, bounds, module types, parameter ranges/enums, unique IDs, known sockets, signal compatibility, input occupancy, instance limits, and acyclic routing. Unknown top-level/module/cable fields and unknown parameters are rejected. Imported patches receive a fresh project ID to preserve existing saved work.

Sequencer buttons retain native tap/Enter/Space activation to cycle forward and wrap. `SequencerStep` captures a single pointer and adjusts scale degrees from the initial press position: up raises, down lowers, with a rest below the lowest note and no wrapping during a swipe. Arrow keys adjust the same range. The range is shared with validation through `SEQUENCER_DEGREES` in the module registry; gesture thresholds and normal/Shift sensitivity live in `CONFIG.sequencerGesture`. Pointer state and click suppression remain local to the button; only degree changes enter the ordinary patch/history/autosave path, grouped per swipe. Pointer cancellation or lost capture clears the gesture. Workspace pinch cancellation uses that same path, so the remaining finger cannot resume note editing or cycle a note on release. Panel dimensions, playback scheduling, and the saved note shape are unchanged.

The current model allows fan-out from an output, one cable per input, and at most one Output module. Mixer has 2–8 separate audio inputs, keeping the original A/B IDs. Empty patches may contain no output and therefore produce no audible signal. Removing a module removes its cables in the same edit.

Merger adds four independent audio inputs (`in1`–`in4`) and one audio output (`out`) using the ordinary module/parameter shape. It can receive instruments, effect returns, or other mergers; normal input-occupancy and cycle rules still apply. It cannot accept pitch, trigger, or modulation cables. Mixer remains a separate fader-based module with 2–8 inputs. Its `inputCount` defaults/migrates to 2; legacy A/B gains and IDs stay unchanged. Extra C–H gain values are initialized for old saves and retained when hidden. `moduleDefinition` resolves active ports, controls and width; inactive ports fail validation. `setMixerInputCount` removes discarded input cables and clears resize overlap in one Undo edit. The runtime owns eight independent input gains, ramps active values, mutes hidden channels and disconnects them all on disposal. Merger keeps its four-input signal contract and uses one five-column knob row aligned with the shared footer, in a smaller 320×248 enclosure.

Switch stores optional module-only `switchCues` (`{bar, input}`), plus registry defaults `automatic`, `repeat` and `loopBars`. Bar numbers are one-based; validation requires a unique bar 1 cue, bounded inputs/bars/count, and complete repeat coverage. A wholly absent legacy schedule migrates to disabled Auto with the original manual selection preserved; partial/invalid schedules fail import/storage/API validation. `setSwitchSchedule` applies a copied/sorted draft atomically through patch history. The module-owned `SwitchScheduleEditor` edits one cue at a time through previous/next controls, retaining the original 320×300 enclosure and bottom sockets. Its native form replaces the input-key view while open; it creates no workspace modal or App-level dialog state. Cancel/Escape discards the local draft and returns focus to Schedule; Use schedule applies it in one history edit and returns to the keys. Restored cue/repeat data remounts the draft on Undo/Redo, while transport ticks and unrelated edits preserve in-progress fields. Other workspace controls remain available during editing. All existing port IDs, dimensions and saved/example positions stay unchanged.

`switchInputAtBar` is shared by audio and the key lights. AudioEngine retains the current and look-ahead tick times, schedules native Switch input gain targets at those exact times, and suppresses redundant targets within a section. A small per-runtime signature keeps ordinary patch edits from disturbing queued cues; schedule/mode/tempo/meter edits hold the current gain values, cancel future targets and rebuild the Switch’s pending events on the same queued musical ticks. Stop, graph replacement and disposal clear pending changes. Native ramps preserve continuity; upstream sources/effects keep their clocks and tails. The one-pass final cue holds, or the entire pattern repeats to bar 1. 4/4 uses sixteen sixteenths per bar; 3/4 and 6/8 use twelve.

Automatic playback never writes `parameters.selected` or adds history/autosave edits. Explicit input keys save the chosen input and disable Auto together; toggling Auto rejoins the current bar. The panel subscribes only to the read-only playback bar snapshot, so React renders/lights cannot become the musical clock. Stop shows the saved manual selection for live playing and the next Play begins at bar 1. The user-facing Switch demo routes drums and a sequenced melody through a two-bar repeating schedule.

## Edit history

`domain/history.ts` owns the in-memory `PatchHistory`: current patch, bounded past/future snapshots, and grouping boundaries. `useStudio` bridges it to React and the existing autosave/flush lifecycle. Every edit replaces changed data rather than mutating earlier snapshots; unchanged subtrees and embedded PCM strings are shared. A structural equality check skips unchanged values (including equivalent nested data returned by validation) before touching timestamps or either stack. A real edit discards redo; undo and redo update `updatedAt` and end grouping. Opening a patch clears both stacks and grouping. History is session-only, capped by `CONFIG.historyLimit`; saving persists the current patch, not history.

App capture handlers begin an interaction on pointer-down or a fresh slider/step/XY adjustment key. Commits in that interaction share a unique group, with optional control-specific keys, regardless of pauses. Pointer-up/cancel, adjustment-key release, window blur, and hidden visibility end it. A new interaction never joins the preceding one. Typing outside an interaction retains the timed field grouping configured by `CONFIG.historyGroupDelayMs`. Module movement previews still commit only on release. Undo/redo also clear pending cable and module movement previews so transient endpoints cannot survive a restored graph.

The workspace keeps its icon buttons, available in focus mode. Cmd/Ctrl Z, Cmd/Ctrl Shift Z, and Ctrl Y operate patch history from sliders, selects, keys/pads, and the settings dialog. Text inputs and contenteditable fields keep native text undo; other dialogs block patch shortcuts. `historyShortcut` excludes composition/Alt-modified events. Restored snapshots follow the normal audio update/disposal path and autosave without starting or stopping transport or recording. Camera navigation, live notes, saved takes, dialogs, and browser appearance remain outside patch history. History does not add any fields to patch schema v3.

## Audio lifecycle

`audio/session.ts` coordinates the page-wide, optional `navigator.audioSession` API. Engine activation acquires `playback` before creating/resuming Web Audio so supported iPhone browsers do not treat the studio as ambient sound silenced by Silent mode. Stop, idle suspension, failed activation and disposal release the request; browsing, imports and passive displays do not acquire it. Multiple owners share the policy, and the last release restores the preceding type. Mic sampler capture acquires higher-priority `play-and-record` before requesting permission, releasing it when tracks stop or permission/capture is cancelled or fails. Ending capture returns an active studio to playback; stopping the studio cannot override ongoing capture. Missing/rejected APIs leave ordinary Web Audio available, with Silent mode off as the older-browser workaround. This declares audio policy without requesting microphone permission for studio playback or output recording. See the [Audio Session specification](https://www.w3.org/TR/audio-session/) and [WebKit's category mapping](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/audiosession/DOMAudioSession.cpp).

`useAudio` owns exactly one `AudioEngine`. A user Play/Record or live instrument gesture creates and resumes the context. Stop suspends it. Live gestures can resume the audio device without starting the transport; after the final held key or hit, an idle timer allows a configured three-second effect tail, then suspends it. The UI distinguishes transport playback from an active audio device. Unmount stops recording, disconnects owned nodes, and closes the context. Engine disposal detaches references and resets graph identity synchronously before closing the old context asynchronously, allowing safe reuse during development Fast Refresh. Hook transport state is reconciled when effects restart. StrictMode double mounting is intentionally not used around live context ownership.

Topology is identified by module IDs/types and cables. Moving panels and editing parameters does **not** recreate the graph. A topology edit disposes the previous runtime graph and creates a new one. This simple first implementation can produce a transient on rewiring; future versions may crossfade graph replacements.

Each factory returns named input/output endpoints, an `update` function, a `dispose` function, and optionally a pitched voice. Audio/control cables connect native AudioNode or AudioParam endpoints. Pitch cables are event routes from sequencers or live keyboards to oscillator voices. Trigger cables route pad sound/velocity events to drum runtimes; neither event type becomes a native AudioNode connection. An unsequenced oscillator sustains the patch root note; a sequenced oscillator follows its pitch cable and gate envelope.

The Merger factory derives its inputs from the registry. Each socket owns a separate gain node controlled by its matching `in1`–`in4` parameter (0…1, default 1), feeding a shared sum gain whose `level` defaults to 0.5. All five gains are smoothed independently. Separate nodes preserve independent paths even when the same source is patched to multiple inputs; Web Audio would collapse duplicate connections to a shared endpoint. Levels are summed without automatic normalization, so attaching a cable does not rebalance existing sources. Disposal disconnects every input and the sum. Input knobs use the normal parameter/history/autosave path; their amber indicators show cable occupancy, not audio metering. The Output module shows the real signal. Merger styling is in `module-finishes.css`; its original 320×336 footprint and sockets are unchanged.

`parseProject` explicitly migrates v1/v2 Merger saves missing all four input parameters to registry defaults, preserving their original sound and Sum level without mutating the source. Partial groups, invalid levels, and unknown parameters are rejected. The patch stays v2; earlier releases cannot read the new input parameters.

`TempoIndicator` shares one printed metronome symbol between the main tempo control, synced module rates and Help. Hover, keyboard focus and touch reveal an explanation; it never changes parameters or starts audio. Sample & Hold derives its clock source from the actual TRIGGER IN cable: external mode shows a lightning marker and TRIGGER IN, replacing the inactive rate selector; unplugging restores the retained rate. These are UI-only indicators; audio scheduling, serialized data and dimensions are unchanged.

The scheduler wakes every 25 ms and queues notes/hits 120 ms ahead using `AudioContext.currentTime`. Its shared tick is one sixteenth-note. Drum machines advance every tick; each melodic sequencer independently selects `rate`: `1/4`, `1/8` (default), or `1/16`, advancing every four, two, or one ticks respectively. Rate options, tick divisions and defaults live in the module registry. Step index is derived from the absolute transport tick, so live rate changes join the new grid rather than resetting a local clock. Gate scales with that sequencer's step duration. The release gap contracts for short steps/long gates so the release always follows the hold and ends before the next onset. Existing eighth-note envelopes retain their timing.

`AudioEngine.onTick` publishes the absolute tick through audio-aligned visual timers; `SequencerPanel` derives each module's light from its own rate. UI timers never schedule sound. Both pattern lengths repeat independently of the displayed time signature; 3/4 and 6/8 currently share three quarter-note beat groups. Tempo/rate edits affect the next scheduling window, so a short already-queued segment may retain the previous timing. Stop clears pending visual timers; Play restarts all patterns at step one.

Step rate is an ordinary saved module parameter, with the usual undo/redo, autosave and offline behavior; editing it never rebuilds the audio graph. `parseProject` explicitly migrates v1/v2 sequencers missing `rate` to `1/8` without mutating saved input, while explicit unsupported values are rejected. Patch version stays v2; earlier releases reject the new parameter. The native selector replaces the old passive readout within the original 260×304 panel and leaves all socket geometry unchanged.

Signal chain: Output module gain → dynamics compressor → master gain → analyser → speakers and recording destination. Filter/resonance and delay feedback have bounded parameters. The compressor softens peaks; this is not a mastering limiter. Reverb builds a local random decaying impulse, so recreating the graph produces a slightly different ambience. Noise is also generated locally.

## Performance instruments

App-wide `user-select` and WebKit's prefixed selection/callout rules prevent touch gestures from selecting printed labels, toolbar text, and guides. Inputs, textareas, and editable fields explicitly retain native text selection and paste. `useStudioTouch` installs native non-passive listeners on the app shell: multi-touch and WebKit gesture defaults cannot magnify the studio, while Ctrl+wheel remains camera zoom only in the rack. Single-touch starts on keys/pads also cancel the native loupe/default mouse emulation; their pointer and keyboard handlers still own the actual notes/hits. A scoped context-menu guard protects held performances. Ordinary buttons, editable fields, and one-finger list/dialog scrolling retain their native defaults. Listener cleanup follows the app lifetime; focus and keyboard access remain available.

The bottom-left Select/Hand controls have distinct pointer ownership. Select (Play / edit) reserves any gesture beginning on a module for independent controls; only touches that all begin on empty rack space can become a pinch. Hand (Pan / zoom) intercepts pointer-down before module handlers, so a drag pans and a pinch navigates over instruments without editing/playing them. Pointer clicks and double-clicks are suppressed in Hand; keyboard activation remains accessible. A tool change cancels active touch owners and camera edits before clearing the touch/pinch state. Global release, blur and hidden-document cleanup prevent stale touches, and shared knobs retain the owning pointer ID so another finger cannot replace or finish their drag. Mixer faders also capture their own pointer explicitly, retaining native range keyboard/change semantics while mapping clamped vertical positions to gain until up/cancel/lost capture. Their CSS thumb height drives the scaled travel calculation, avoiding a jump when grabbing the thumb. Mode and camera state stay outside serialized patches and history.

Keyboard stores registry-validated `keyCount` of 25, 37, 49 or 61; missing legacy counts explicitly migrate to 25 without changing IDs, notes, positions or cables. The default enclosure remains 428×360; each extra octave adds 182px through `moduleDefinition`, which also drives bounds, demo layout and the shared footer/socket geometry. `setKeyboardKeyCount` applies count and any clearance move in one Undo edit, preserving all pitch cables and other modules. The panel derives the white/black key spacing and note range from count, releases held tokens on resize, and uses actual held-note state for pressed styling rather than native `:active` (which remains on the initial touch target during a slide). Its canonical guide demo now uses 37 keys.

Keyboard pointers capture on their stable keybed, independently by pointer ID. Moves hit-test visible keys in viewport coordinates, respecting raised black keys and canvas transforms. A swipe changes its existing token's note, sends the new note-on before the old note-off, and releases the old pitch only when no other token holds it. Outside coordinates project onto this keyboard’s nearest edge, retaining capture and continuing horizontal note selection above/below the keys. Left/right overshoot selects the nearest end key; each finger remains independent. Crossing another module never transfers ownership. Pointer-up, cancellation, lost capture, blur, hidden documents, and unmount clear ownership. Workspace pinch cancellation uses the same path. Moving focus to another module releases keyboard/tap tokens while physically held pointers continue until their own up/cancel. Held tokens and their readout stay ephemeral.

`Pad controller` stores a registry-validated `padCount` of 4, 8 or 16 (default 16). `moduleDefinition(module)` resolves its configured footprint and active ports for panels, socket rendering/geometry, validation, placement, camera bounds and demo layout. All sockets stay in one shared bottom row: 4 pads use 300×384, 8 use 432×456, and 16 use 760×456. The original `trigger` port is labelled ALL; stable `pad1`…`pad16` ports carry only their matching hit. `padTargets` combines numbered/shared fan-out and rejects hidden, stale or invalid pad indices. AudioEngine derives the sound from that pad index and uses the current AudioContext time; events still never become AudioNode connections.

`setPadCount` changes count, active cables and any necessary panel relocation in one history edit. Shrinking removes only cables from discarded outputs; re-expansion offers empty sockets, while Undo restores the old count, position and routes. The camera keeps the configured panel in view, pending wires to removed ports are cancelled, and other panels stay put. Explicit migration gives legacy controllers their original sixteen sounds and shared route; only a legacy controller overlapping a neighbour after widening is relocated. Imported invalid counts or cables to inactive sockets fail validation. The pad field guide/demo demonstrates independent kick and sampled-clap routes; Pocket rhythm and Neon chorus keep their sound/contents with spacing adjusted for the wider sixteen-pad deck.

`LiveControls` sends note-on/off and drum/pad hits without mutating serializable project data. Held keys, lit pads, AudioNodes, and live velocity events never enter undo history or autosave. The hook guards asynchronous audio activation: releasing a key before `resume()` completes cancels the pending note, and Stop invalidates pending live gestures.

Keyboard holds have last-note priority per oscillator. Releasing the last note silences the gain envelope; releasing a newer note restores a previously held one. Pointer cancellation, focus loss, visibility changes, window blur, Stop, topology changes, and unmount provide cleanup paths. The keyboard octave and the oscillator octave add together; oscillator detune still applies. Physical MIDI and polyphonic oscillator voices are not implemented.

`audio/drums.ts` builds sixteen kit sounds from short oscillators and filtered noise using editable recipes. Each triggered hit owns its nodes until all its sources end. Stop/disposal disconnects and stops outstanding sources, including scheduled hits. A closed hat chokes a ringing open hat; a configurable overlap limit bounds rapid triggering. Drum level/tone/decay affect sequenced and live hits. The four pattern lanes remain editable independently of the sixteen pad sound mappings; disabling Pattern stops scheduled hits but accepts live triggers.

The _Pocket rhythm_ example connects Keyboard → Oscillator, Pad controller → Drum machine, Drum kit → Drum machine, Drum machine/Oscillator → Mixer → Output. It is available through the example collection alongside the other starting points.

## Microphone sampler

`audio/microphone.ts` owns a single opt-in `getUserMedia` / MediaRecorder audio-only capture (requesting speech processing off to preserve musical transients), separately from the studio AudioContext and its output recorder. No microphone stream is connected to speakers or the recording destination. `useMicrophoneSampler` tracks its requesting/recording/processing lifecycle and module/project owner; all of this is ephemeral. Only pressing Record mic requests permission. Cancel, global Stop, module removal, project switching, page hiding, and unmount invalidate pending permission/decoding and stop every acquired track. Late permission grants are immediately released. A normal Finish or four-second timeout stops the device before silent decoding, downmixing, and resampling. Recorder padding is trimmed to the four-second PCM limit. Permission/device/decoding failures leave the existing clip intact. App refresh is blocked during capture/processing.

The saved `samples.clip` uses the existing validated PCM format and shared project budget. This is additive to v2: existing patches need no migration, and an empty sampler is valid and silent. `useStudio.setSample` validates the latest patch before committing a sample edit, preserving undo/autosave and atomically rejecting over-budget replacements. Drum kit imports use the same commit path.

`audio/mic-sampler.ts` reconstructs a buffer only when PCM changes. Registry controls `trimStart`/`trimEnd` store normalized 0…1 positions with `start < end`; `parseProject` explicitly migrates old sampler modules missing the entire pair to 0/1 without mutating their saved data. Partial/out-of-range/crossed trim is rejected. The patch stays v2, and earlier app releases reject these new parameters. `domain/samples.sampleRegion` turns trim into bounded frame offsets/durations shared by runtime playback, WAV export, duration displays, and live idle timing. The original PCM remains intact and still counts toward the sample budget. Native trim rails and a dimmed waveform selection use the usual parameter/history/autosave path; each drag is grouped for Undo. Reset restores 0/1. New recordings and Clear reset trim atomically through `setSample`; failed/cancelled replacements keep both the clip and trim. Trim edits affect the next hit, leaving an already scheduled envelope intact. Each preview or pad-trigger event starts a one-shot on `AudioContext.currentTime`; top-bar transport Play does not trigger it. All incoming pad identities select the same clip and velocity sets the hit gain. Level is smoothed; Speed applies to the next hit so its start/end envelope stays aligned with the audio clock. Retriggers retire the previous voice with a short fade and a bounded tail count. Stop, replacement, graph rebuild, and disposal release all sources and gains. The live idle tail includes the full clip duration at its selected speed plus effects time. Pad-trigger audio output uses ordinary routing to effects/mixers/Drum kit inputs; trigger/pitch/audio incompatibilities and cycle checks remain intact. Play snippet instead uses a separate engine-owned sampler runtime connected directly to the device destination. It uses the saved trim/Speed/Level, bypasses patch routing, Output mute, effects and master volume, and is excluded from the studio recording bus. Only this preview runtime is retriggered, avoiding a doubled dry/routed hit. The hook tracks preview activity separately from live-performance activity: `active` still protects updates and drives audio-aware rendering/idle cleanup, while `transportActive` controls the main button and Space shortcut. A preview alone leaves Play available; starting transport during it keeps the preview running. Live instruments and microphone capture retain their existing Stop control. Stop silences it; project switches, module removal, previewing a different sampler and engine disposal release it. Clip replacement/Clear uses the normal sample-runtime cleanup. Preview and routed sampler runtimes report outstanding audio-clock end times so a trim/rate edit cannot shorten the idle allowance for a hit already playing.

`MicSamplerPanel` provides a slate-blue handheld-recorder enclosure, passive saved-waveform display, recording state, and accessible native controls. Download WAV writes the selected mono PCM frames at their original speed/level as a standard WAV for existing Drum kit sample import or use outside the app. Saved playback and WAV export need neither microphone permission nor a connection; new capture depends on secure-context/device permission support. Physical Safari/iPad microphone behavior still requires device verification.

## XY Effects

XY Effects uses the ordinary parameter map: registry-bounded `x`/`y` (−1…1, positive Y upwards), `mix` (0…1), and four validated effect IDs (`topLeft`, `topRight`, `bottomLeft`, `bottomRight`). Corner/effect identities and `xyBlend()` live in `domain/xy-effects.ts`; the registry owns dimensions and defaults. Compatibility derives from its audio input/output sockets.

The pad updates both coordinates atomically through the standard patch/history/autosave path, with a per-gesture group. It retains position on release, bounds out-of-pad drags, and cancels on lost capture, focus/window loss, hidden documents, and workspace pinch. Arrow keys, fine Shift arrows, Home/Centre, and labelled native axis sliders provide keyboard and assistive access. Corner selectors are native selects. The field guide never starts sound.

The audio runtime keeps a fixed parallel graph: low-pass Filter, a bounded feedback Echo, oversampled soft-clipping Grit, locally generated stereo Space reverb, high-pass Thin, and Clean. Static effect settings are centralized in `CONFIG.audio.xyEffects`. Bilinear corner weights are multiplied by maximum axis distance from centre and Mix; the remainder is dry. Weights are nonnegative and sum to one. Selecting an effect more than once adds its weights to one bus rather than duplicating nodes. Every bus gain ramps using the shared smoothing time, so movement and reassignment avoid topology changes. Effect inputs run continuously, allowing existing echo/reverb tails to be heard when blending towards them. Disposal disconnects every node and the feedback loop and releases impulse/curve buffers. No downloads, microphone permissions, or additional audio sources are required.

## Drum kit voice assignment

Drum kit adds a distinct `kit` signal: KIT OUT → Drum machine KIT IN. The existing v1 drum pattern keys (`kick`, `snare`, `clap`, `closed-hat`) remain stable lane identities, displayed as voices 01–04. Kit parameters use those same IDs to select a built-in recipe, `sample`, or `input`; defaults remain in the registry. Both sequenced hits and live audition/first-four-pad triggers resolve an assignment exactly once. The remaining twelve pads retain their literal sound identity. Unlinked drum machines use the original sounds. Fresh Pocket rhythm examples include a connected kit without changing the original rhythm or sound.

Kit runtimes own four independent passthrough buses. KIT links explicitly connect those buses to private per-lane drum-runtime inputs; they are not ordinary public audio sockets. Each receiving drum machine owns its envelopes, sample buffers, and one-shot sources, so fan-out remains independent. Ordinary external audio is gated on each hit with Input decay multiplied by drum Decay; it is not recorded, buffered, or pitch shifted. Mic sampler → kit routes, direct or through serial effects, are resolved separately by `kitSamplerPaths` and `kitSamplerSources`. For an `input` voice with a linked sampler, each receiving drum runtime decodes the saved PCM once and schedules its own source per hit, starting at the selected offset for the complete selected duration. It never gates the running sampler bus or triggers the sampler’s monophonic audition runtime. Source rate combines sampler Speed and Drum Tone, with sampler Level and velocity applied per hit; drum Level is smoothed on the common output. Changes to clip/trim/source settings apply to new hits; previous hits own their buffer and envelope until completion. Empty linked samplers stay silent. Serial effects between the sampler and kit use a private rack per receiving machine/lane; see Sampler effects before Drum kit below. Mixer/Merger/Switch routes retain ordinary live streams. A silent looping source supplies audio-clock `onended` cleanup for each input envelope, including scheduled hits. Cleanup detaches only that hit’s connection, is idempotent across Stop/late callbacks, and uses the existing overlap bound. Topology replacement/removal disposes buses, buffers, sources, and connections. Parameter/assignment edits leave existing hits to finish and affect the next scheduling window.

Drum kit modules may contain `samples`, a map of known lane IDs to `{ name, pcm }`; Mic sampler modules use the same map with one allowed key, `clip`. Other module types reject sample data. PCM is base64 little-endian signed 16-bit mono at `CONFIG.samples.sampleRate` (24 kHz). This additive optional v1 field needs no migration; old project shapes/defaults still validate. Untrusted imports use a pinned, locally bundled Mediabunny demuxer and backpressured `AudioSampleSink` rather than whole-file `decodeAudioData`. Only local single-file formats are enabled (WAV, MP3, MP4/M4A, ADTS/AAC, Ogg, WebM, FLAC); playlists and URL sources are excluded. Actual decoded frame counts enforce four seconds regardless of duration metadata; channel/rate checks (eight channels, 192 kHz) run before decoder creation and on each output, and cumulative decoded float audio is capped at 16 MiB. Each sample is closed in `finally`; input disposal closes the decoder and its look-ahead queue on success, error, or a fifteen-second timeout. Unsupported compressed codecs fail closed with PCM WAV guidance; PCM WAV works without WebCodecs. The bounded mono buffer is silently resampled by an OfflineAudioContext to 24 kHz before encoding. Only internally recorded, time-limited microphone blobs and studio takes use native whole-blob decoding for browser recording compatibility. Four seconds and 20 MB remain the per-file limits; saved PCM is independently validated at import/storage/API boundaries. The total encoded sample budget is 1,024,000 characters per patch (about sixteen seconds), and JSON import/API requests share a 2 MiB limit. Samples stay inside the patch rather than relying on URLs, IndexedDB IDs, or external services. Browser library quota can still be exhausted by multiple sample-heavy patches; the existing visible save failure/export path applies.

`configureKit` synchronously reconstructs AudioBuffers from validated PCM only when the data changes, avoiding asynchronous loading during playback. Sample playback starts at the scheduled hit time and follows drum Tone/Level. Imported and linked sampler clips are full-length overlapping one-shots. Their Decay release is a tail fade over the original playback duration: 1× or higher uses only a short click-prevention edge fade; below 1× fades the final `(1 - decay)` portion of the clip. Decay never shortens the source, changes speed, or steals another hit. The existing per-machine hit bound remains in place. Empty sample/input modes are silent. `drumLiveTailMs` includes sampler trim, combined Speed/Tone, imported samples, and live-input envelopes. Drum runtimes also report their actual outstanding end times; the live idle timer uses whichever is longer, plus the normal effect tail, so changing a later hit’s settings cannot suspend an older long voice. This adds the possible sample/input duration to the normal idle effect tail so tuned samples are not cut short by live-audio suspension. Sample import checks module lifetime and commits data plus its selection atomically through validation/history/autosave; a removed module or switched project cannot receive a late import. Browsing the guide and importing samples never starts studio audio.

## Switch audio selector

Switch is an additive module type in the ordinary v2 parameter model. Registry ports `in1`–`in4` accept audio and `out` carries the selected source; `selected` is an integer from 1 to 4, defaulting to 1. The existing validator rejects missing, fractional and out-of-range selections, incompatible sockets, occupied inputs and cycles. Older patches remain unchanged; older app releases cannot open patches containing Switch.

The factory owns four distinct input gains feeding one output gain. All inputs start closed; updates target unity for the selected input and zero for the others using the shared audio smoothing time. Rapid selections retarget the existing gains, keeping clocks, sources and upstream effects running without rebuilding the graph. An unpatched selection therefore settles to silence. Disposal disconnects all five nodes. This is an audio selector, not an event/pitch/modulation router.

`SwitchPanel` renders native pressed buttons with connected-source labels, a visible selected lamp and keyboard focus. Normal parameter edits provide Undo/Redo, autosave and export. Its burgundy bakelite enclosure and ivory latching keys live in `module-finishes.css`; dimensions and socket geometry remain registry-driven. The field guide provides registry-derived compatibility and a worked dry/echo comparison. Browsing it remains silent.

## Recording and persistence

MediaRecorder receives the engine's MediaStreamAudioDestinationNode stream, so no microphone/device permission is needed. MIME format is negotiated per browser. Chunks are assembled into a Blob and saved in IndexedDB after Stop recording. If storage fails, the native recording downloads automatically. Object URLs used for previews/downloads are revoked. Ten minutes is the configurable take limit.

Each saved take offers WAV (16-bit PCM), MP3 (192 kbps) and Original downloads, including legacy takes with no storage migration. Original returns the exact captured blob and extension. Converted downloads silently decode the trusted, internally captured take in an OfflineAudioContext at 48 kHz; this avoids WebCodecs requirements and never activates speakers or requests a device. Whole-take decoded PCM consumes memory proportional to duration (about 230 MB for a ten-minute stereo take), so the dialog serializes conversions. The decoded channel buffers transfer to a dedicated worker rather than being copied. The worker encodes small blocks, preserves mono/stereo order, bounds frames to the recording limit plus five seconds of codec padding, clamps PCM peaks and rejects invalid samples. LAME's output blocks are copied before reuse and flushed to retain the last partial frame. Conversion cannot improve the original compressed capture's fidelity.

`useRecordingExport` owns an AbortController; closing the dialog suppresses any late download, and encoding completion/error/abort terminates the worker. Native decoding cannot be interrupted, but its result is discarded after cancellation. The UI shows decoding/encoding status and prevents concurrent downloads. Decode/worker failures retain the take and show an inline alert beside it with Original-download guidance. Export rates, bitrate and block size live in `CONFIG.audio.recordingExport`. The pinned, unmodified `@breezystack/lamejs` package runs only in the bundled worker; its acknowledgement/license lives in `public/licenses/lamejs.txt`. The generated worker and license enter the normal atomic offline release. No server, upload, external script, schema change or stored conversion is involved.

`domain/project-persistence.ts` owns session-only persistence policy, separate from patch data and history. `useStudio` marks examples, module-guide demos and the first-visit starter temporary. All automatic writes—debounce, project-switch preservation, pagehide/hidden visibility and ordinary flush—pass through this gate. Edits, Undo/Redo, performance and recording keep the same temporary identity. My patches omits the temporary active project and leaves the prior saved pointer intact. Reload restores that owned patch (or the first-visit chooser when none exists). Successful explicit Save writes the latest snapshot and promotes it to ordinary autosaving; a failed write leaves it temporary and retryable. New/imported/library patches use normal persistence. No template flag enters Project v2 or exports, and existing saved demo copies are not removed. Manual update refresh is blocked until a temporary demo is explicitly saved or the user opens an owned patch, preventing update activation from implicitly saving or discarding it. Saved takes remain independent.

Owned patches autosave to browser localStorage after 650 ms and flush on pagehide or hidden visibility (including mobile suspension). A manual Save optionally calls the Node API only when online on a known loopback hostname and after a Patchwork health response; the confirmation distinguishes successful server saving from browser-only saving. Public/static installs never attempt API calls. The library merges local and eligible server copies by ID/update time. Browser quota failure remains visible. Recordings and patches are origin-specific and are not synchronized between local/hosted previews or necessarily between Safari and a home-screen installation.

## Offline application lifecycle

Production builds include a standalone manifest, device icons, and a generated service worker. Its asset list and content revision derive from the complete Vite output. Atomic installation caches one complete release; cache-first requests cover only enumerated GET assets and root navigations. All resources are bundled locally. API calls and recording data never enter the app-shell cache. Patch saving, synthesis, and IndexedDB recording work independently of connectivity.

`useOffline` registers only in production on secure origins, checks readiness through the active worker, and exposes status in the footer and installation dialog. Updates wait for all old clients to close by default. The update notice and offline dialog offer a deliberate Refresh now action; it is disabled during audio startup/playing/live sound or while a recording is being made/stored. `useAudio.recordingPending` spans recording startup through final IndexedDB completion (or download fallback). `useStudio.flush` saves the latest snapshot synchronously, preventing a reload inside the autosave debounce window; a storage failure leaves the session open with export guidance.

`useOffline` checks on launch, reconnect, foreground return, and a configurable visible interval. It reports check errors separately from offline readiness. Dismissing the notice leaves the waiting update accessible in the offline dialog. On Refresh now, the waiting worker verifies the complete cache and a single requesting window before using `skipWaiting`. No other client can be switched during its unknown audio state. Controls become inert during activation; only an explicitly requesting page reloads on controller change, with timeout/error recovery. First installation and other controller changes never reload the page. Existing older clients acquire this UI through the original close-all-windows update path. Activation removes only outdated Patchwork app-shell caches. The dialog can request persistent storage without promising browser approval. Safe-area padding and bounded viewport height support installed tablet/phone windows. See [offline design](OFFLINE.md) for installation, limitations, and device QA.

`wrangler.jsonc` configures the assets-only **patchwork-studio** Cloudflare Worker at **https://patchwork.jameslane.dev**, excluding the local Node API. There is no application Worker script, hosted database, or cloud sync dependency. The Custom Domain configuration manages DNS/HTTPS through Cloudflare; `workers.dev` and preview URLs are disabled. Missing assets return 404 rather than falling back to HTML. Cloudflare Workers Builds is the production deployment path after the one-time GitHub connection is enabled: pushes to `main` run `npm run build:ci`, then `npx wrangler deploy` only on success. `scripts/ci-build.ts` recovers full Git history from shallow clones, rejects dirty checkouts and runs formatting plus the complete check/build pipeline. `.node-version` selects Node 22. Review branches can use the same CI build followed by `npx wrangler preview` to publish separate public test links; `preview_urls: true` and an empty `previews` block enable these without publishing production. All file changes (including documentation) can trigger a versioned build. `npm run deploy` remains available for manual recovery. Deployment credentials and local Wrangler state are never committed.

Node persists each validated UUID to `.data/<id>.json` using a unique temporary file and atomic rename. A corrupt stored patch is skipped during listing. This is a single-user local adapter, not a database or multi-user synchronization system. Request JSON is bounded to 2 MiB. The service listens on `127.0.0.1`; it is not ready for unauthenticated public access. Before parsing JSON or serving files, `server/local-access.ts` requires an exact configured loopback Host and the listener’s actual port, rejects foreign/null Origin values and cross-site Fetch Metadata, and ignores forwarded headers. Same-origin local requests, the fixed loopback Vite development origins, and Origin-less local CLI clients remain supported. Vite rewrites the proxy Host to the Node authority. These checks defend the local adapter against DNS rebinding without adding accounts or exposing an API on the public host.

Browser security headers apply to every Node response and to static production assets through `public/_headers`. Their baseline matches `CONFIG.securityHeaders` in an HTTP regression: scripts/workers/connects stay on-origin, external framing/objects/forms/base URLs are blocked, blob audio remains playable, and device policy permits same-origin microphone use while disabling camera/geolocation. Inline styles remain allowed for React’s module/camera controls. The worker and manifest retain their no-cache overrides; cached HTML retains the policy offline.

Long braided cables cap sample count, and their geometry is relative to the source socket, so camera-only pans translate cached strands instead of rebuilding them.

Library placement uses captured pointer events rather than relying on native HTML drag-and-drop, which is inconsistent on touch devices. `useModuleLibraryDrag` owns the movement threshold, click suppression, cancellation, and release coordinates; mouse users can drag a row, while touch/pen users drag its grip so normal list swipes scroll. Workspace hit-tests the visible rack, transforms through the current camera, snaps the position, enforces instance limits, and commits once on release. Successful drops retain the view. The + action searches around the visible centre and existing panel edges for a nearby non-overlapping position, rather than exhausting a fixed slot list; the new panel is framed afterwards. Invalid releases and cancellation add nothing.

**More → Studio settings → Theme** stores `system`, `light`, or `dark` independently of patch data in the key configured by `CONFIG.appearance.themeKey`. Missing, invalid, or unavailable storage defaults to System. `main.tsx` applies a saved override before mounting; `useTheme` owns the current visit's choice, updates the browser theme-colour metadata, and cleans up its system-change listener. Failed persistence keeps the selected theme for the current visit and shows a notice.

CSS `color-scheme` and `light-dark()` resolve System before React renders and follow live OS changes. Explicit document theme attributes force Light or Dark. Night colours are centralized in `styles.css`; chrome, workspace, dialogs, library, examples, and guides use them while preserving existing light colours. Physical `.module-panel` elements keep their original inherited text colour and a light native-control scheme, so enclosure palettes, instruments, sockets, and cables are unchanged. Appearance changes never edit patch data, history, positions, or audio topology; all theme resources are in the normal atomic offline build.

**More → Studio settings** includes a browser-wide cable style choice. Classic preserves the existing signal/source colours. Braided uses both endpoint modules' enclosure colours for two interwoven strands. The `--enclosure-*` CSS tokens in `module-finishes.css` supply both panel faces and braid strands, keeping the weave aligned with the physical finishes (cream sequencer, ochre oscillator, forest-green filter, etc.). Registry accents continue to colour plugs independently. `cable-geometry.ts` samples the existing cubic curve and alternates strand depth at crossings; distance-based phase keeps the weave density consistent on horizontal, vertical, and long cables. Geometry is memoized by endpoint span/style, so playback, origin rebasing and unrelated parameter edits do not regenerate it. Spans are calculated before rebasing to avoid tiny floating-point changes invalidating detailed braid paths. Cable hit areas and socket geometry are unchanged; the pending cable stays neutral until both endpoints are known. The weave is static and adds no animation.

`domain/preferences.ts` validates the stored cable style and opacity, falling back to Classic and 100% for missing, invalid, or inaccessible browser storage. Separate localStorage keys, defaults, and the opacity range/step live in `CONFIG.appearance`. The settings slider adjusts opacity from 0–100% for each complete connected cable (including braid, highlight, shadow, and plugs). At 0%, cable hit paths stop intercepting underlying controls; sockets remain available for rerouting. The pending connection stays visible at full opacity. Saving failure retains the choice for the current visit and shows a notice. Appearance is not part of the patch, patch exports, undo history, or audio graph identity; opening/importing another patch preserves the browser preferences.

The visual direction is a collection of distinct physical instruments, as explicitly requested by the user. Surfaces may differ in colour, material, size, silhouette, and controls. Enclosures include walnut-trimmed charcoal, violet polymer, ochre/green/blue/plum enamel, graphite, aged cream, and brushed aluminium. Instrument surfaces use CSS gradients, layered borders/shadows, fixed tick rings, rotating knob markers, metallic socket rings, and panel screws. SVG traces and cables avoid image assets. Actual waveform/level displays read the analyser. Performance layouts live in `components/instruments.css`; module finish palettes and material details live in `components/module-finishes.css`. Shared panel/knob mechanics read inheritable CSS custom properties declared on `.module-panel` in `styles.css`. The mixer has real vertical native range inputs, with channel values and persistence identical to the original knobs. Selected utility/effect widths are smaller, so old saved positions remain valid. Painted rails and decorative wood cheeks do not change the structural border box; cable math remains unchanged. Wide performance modules use registry dimensions like every other module. New modules added with + are framed by the camera; drag/drop retains the current view. Keep the hardware feel for modules; keep application chrome restrained.

## Sampler effects before Drum kit

`kitSamplerPaths` traces each kit audio input backward through serial Effects modules to a Mic sampler. `kitSamplerSources` supplies the resulting saved clip references for per-hit trim/Speed/Level/Tone/Decay and live-idle timing. Mixer, Merger and Switch routes retain live-input gating; no mixed source is implicitly retriggered. Patch data and socket contracts are unchanged.

`audio/kit-effects.ts` owns a persistent private effect rack per receiving drum machine/lane. Drum sample envelopes feed that rack, whose output returns to the machine’s level bus. This preserves overlapping one-shots and delay/reverb tails without duplicating source audio into other consumers. Racks follow the original modules’ parameter edits and external modulation, and dispose their nodes and specific modulation connections before the main graph is disposed or rewired. Racks persist after a hit ends; the normal live-audio tail allowance follows the final sample. Ordinary sampler pad playback and dry preview keep their existing routes.

## Modulation sources and receiver contracts

The catalog now contains 21 types. Envelope (`envelope`), Mod sequencer (`mod-sequencer`), Sample & Hold (`random-mod`) and XY controller (`xy-controller`) produce native control nodes. New controls use the existing numeric parameter map and rate enum; validation checks all bounds and the clock rate. No existing parameter/default, patch version or sample encoding changed. Every socket, including new modulation inputs, renders in the shared bottom footer. `PortDefinition` has no position override: `ModulePorts` renders the full registry port order, and `components/socket-geometry.ts` derives matching cable endpoints from the same evenly spaced row. Receiver footprints and saved port IDs stay unchanged; adding ports reflows the footer rather than placing sockets on the panel face.

`audio/modulation.ts` retains the original LFO/Filter control scale: a full-depth new source emits ±1500 units (Filter Hz), with Envelope unipolar. `boundedModulation` normalizes and clamps at new receivers. Oscillator modulation adds ±1200 cents independently of Fine tune and event-driven base frequency. Mic sampler SPEED MOD uses the same bounded detune bus. LEVEL MOD is a clamped 0–1 multiplier of the existing Level, with an unpatched unity bias and a patched zero bias; negative control values mute. No control signal is connected directly to the master audio bus.

`AudioRuntime.scheduleControl` receives shared audio-clock ticks from the existing look-ahead scheduler. Mod sequencer and clocked Sample & Hold schedule ConstantSource offsets; rate edits join the current transport grid. A Sample & Hold trigger cable replaces its transport stepping. Keyboard/Step sequencer pitch-event fan-out can target Envelope `gate`; gate release is independent of oscillator envelopes. Envelope explicitly schedules both start and peak/hold anchors, computes retrigger values from its own bounded event plan, and returns to zero on release/Stop. Pad/manual triggers create attack/release sweeps. Editing a held keyboard note’s parameters does not retrigger its envelope. Stop clears queued control events; disposal stops every ConstantSource and disconnects owned nodes.

Sampler modulation buses also feed each independent Drum kit player. Each hit detaches only its own AudioParam connections on completion. Dynamic speed uses `AudioBufferSource.start` with the selected source-frame duration, allowing pitch and actual playback duration to vary without reading beyond trim. A conservative two-times base-duration envelope/idle bound covers the slowest supported speed; native completion removes faster voices. Static/no-MOD clips keep the original exact timing. Consumers are silenced before producer buses are disposed during topology rebuilds and engine disposal, avoiding invalid targeted disconnects and leaked voices.

`ControlScope` draws measured output history and numerical values from lazy, engine-owned Analyser taps. It samples visual history at the shared visualization cadence without advancing musical time or rerendering module trees. Taps disconnect before topology replacement/disposal. Idle screens stop their animation loop; reduced-motion mode draws the current value as a stationary trace. XY controller remains a separate two-output control surface from XY Effects’ four-corner audio processor.

Moving parts is the ninth example, with 13 non-overlapping modules and all four new control sources contributing to Output. Neon chorus intentionally retains its original 38-module sound/layout and original-seventeen coverage as the performance fixture; the two examples together cover the expanded catalog.

`components/PortGuide.tsx` provides Getting started’s complete, typed glossary of audio, pitch/gate, control/MOD, trigger, and kit signals. It teaches direction, data vs sound, practical connections, fan-out and input occupancy. Keep it synchronized whenever signal contracts change; browsing it is read-only and requires no audio device.

## Patch deletion

`PatchLibraryDialog` owns named inline Delete/Cancel confirmation, busy/error states, keyboard focus, and the current-patch marker. Open/delete are sibling controls; deleting cannot accidentally open a patch. Its list includes the latest in-memory active project even before the autosave delay. The App stops audio/capture/recording only when deleting the active patch, then calls `useStudio.deleteProject`. Deleting other patches leaves the performance running. Saved takes live in their separate IndexedDB store and are never removed by patch deletion.

`storage.deleteLocally` validates IDs/replacements, records a deleted-ID tombstone under `CONFIG.deletedProjectsKey`, physically removes the patch data from the browser library, and writes the replacement/active pointer together for the active patch. Failed writes roll back the storage snapshots before the hook changes its in-memory project. The hook opens the fresh blank history directly, bypassing `openProject`’s preservation save; a stale debounce checks current identity before saving. `saveLocally`/`saveToServer` reject tombstoned IDs and merged library lists filter them after asynchronous reads. This prevents the active patch, another stale window, or a late server listing from reviving a deleted ID. Tombstones contain only UUIDs, never audio or patch contents; copies imported/opened from templates receive fresh IDs.

Optional server deletion uses `DELETE /api/projects/:id` only after the existing loopback/health verification. The API validates the UUID, inherits local Host/Origin/fetch-metadata guards and unlinks only the repository’s corresponding JSON file. Missing IDs are idempotent 204 responses. Browser tombstones remain authoritative offline; cleanup is attempted after deletion and before subsequent verified server library merges. They are retained to filter/re-clean late writes from older windows. Static/public installs never send these requests and do not depend on the API.

## Purposeful instrument displays

Module screens are optional. Noise is now a 168×220 graphite Level box and Reverb a 180×220 plum Mix box, with no screen, decorative waveform, or display-shaped grille. Their registry footprints shrink around the unchanged, full-sized controls; existing saved positions/parameters/IDs remain valid, and bottom socket/cable geometry derives from the smaller sizes.

`LfoDisplay` renders a fixed-scale two-second Rate/Depth preview when stopped and switches to measured `ControlScope` output when audio is active. The readout can be omitted without affecting other control screens. `FilterDisplay` uses pure biquad magnitude functions and a logarithmic frequency path in `components/instrument-display.ts`, with Web Audio’s dB Q for low/high-pass and linear Q for band-pass. It follows Cutoff/Resonance/mode while stopped and samples the actual upstream MOD output during playback using the engine’s existing disposable meter cache. Unmodulated response plots need no animation; reduced motion uses the base control response and live preference changes stop/restart the drawing loop. `DelayDisplay` previews a four-second dry/echo impulse response from Time/Feedback/Mix while retaining the millisecond readout. Screen slogans are removed from these views.

These are parameter previews/response views, not fake audio scopes. Passive editing creates no AudioContext or native filter. Active visualization uses the existing capped drawing cadence and imperative path/canvas updates, never React state as a musical clock. Display ranges/point counts live in CONFIG.audio.displays; model formulas are checked against native browser `getFrequencyResponse`. Waveform icons remain illustrative library/guide artwork, separate from working panel displays. Keep this policy in future module guides and avoid making every instrument a uniform screen-and-knob panel.

`midi/devices.ts` owns explicit native MIDI access, input ports/listeners and hotplug with permission-generation cancellation. `midi/router.ts` validates messages, filters per-instance devices/channels/note ranges, tracks independently owned notes and sustain, and dispatches transient commands through `audio/live.ts`/`useAudio`. `useMidi` owns the studio lifetime and separately validated local device preferences; its context reaches only the MIDI module's device controls.
